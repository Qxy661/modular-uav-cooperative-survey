# 03 模块间通信与网络化控制

> 本章回答：ESP-NOW 这种"低带宽、无 IP、无原生测距与时间同步"的链路，能不能支撑协同飞行；如果能，通信协议和控制器应该怎么一起设计。

这一章只有 4 篇论文，但每篇都对应一个你会踩的坑：采样/时延/丢包怎么选（3.1）、无线 ROS 的时延抖动怎么降（3.2）、广播式并发传输能不能用于编队（3.3）、丢包和时延下该重传还是编码（3.4）。最后附一段 ESP-NOW 的工程注记，那是协议事实，不是论文结论。

## 3.1 面向控制系统的无线网络设计：综述（2018，IEEE COMST）

**链接**：https://arxiv.org/abs/1708.07353

**做了什么**：系统综述无线网络化控制系统（WNCS）：把采样周期、消息时延、丢包、网络能耗称为"关键交互变量"，讨论协议各层参数如何影响这些变量的分布，以及控制器如何把这些变量纳入设计；总结无线标准与联合优化方法，给出开放问题。

**重点分析**：这篇的框架可以直接套到 ESP-NOW 上：把你们的协同层看成采样控制系统，先量化"采样周期、端到端时延、丢包率、每包能耗"，再决定控制增益与重传策略。多数工程团队反过来做——先写控制器，再测通信，最后发现时延裕度不够。**通信参数是控制器设计输入，不是事后验收项**。

**可参考点**：
- 建立一张通信预算表：控制频率、允许时延、丢包率、每模块每秒字节数。
- 按"时延 > 周期"的临界条件设计降级策略（保位置保持、降编队精度）。
- 把网络能耗（ESP32 射频占空比）纳入续航估算。

## 3.2 Pound：降低无线多机器人网络时延与抖动的 ROS 节点（2017）

**链接**：https://arxiv.org/abs/1707.07540

**做了什么**：分析 ROS 在无线自组网下的 TCP 连接在带宽、时延、抖动上的问题，提出 Pound 节点：支持多 ROS core、按流优先级调度，降低单跳与多跳网络的时延与抖动，并与现有方案对比（含控制过网络示例）。

**重点分析**：**抖动比平均时延更伤控制**。ESP-NOW 有 ACK/重传机制，重传会造成时延抖动；如果所有消息同等对待，控制包会被遥测/日志包挤占。可借鉴的是"控制流优先、状态流次之、日志流最后"的优先级设计，以及在应用层做发送队列与超时丢弃。

**可参考点**：
- 按消息类型分级：控制指令 > 状态广播 > 日志/调试。
- 过期状态包直接丢弃，不要排队发送（旧状态比没有状态更糟）。
- 用序号 + 时间戳检测抖动，纳入控制器的时延补偿。

## 3.3 并发传输用于多机器人协同（2021，Robocom 2022）

**链接**：https://arxiv.org/abs/2112.00273

**做了什么**：指出异步传输策略在快速分发与聚合上的局限，提出用并发传输（concurrent transmission，利用同时发送的干涉叠加）作为替代；给出通信与计算分离的架构，用 5 台异构两轮差速机器人做 leader-follower 速度协同与队形实验，作者报告在多跳、较大场地内达到厘米级空间与毫秒级时间精度、低占空比。

**重点分析**：并发传输的本质是**广播 + 冗余**：多个节点同时发同一消息，接收端靠叠加提高成功率。ESP-NOW 的广播模式在机制上更接近"一对多"而不是"同时同频叠加"，但这篇提醒你：**对于"所有人需要同一份状态"的编队场景，广播/泛洪可能比逐点单播更高效**。代价是需要时间同步与冲突管理。

**可参考点**：
- 状态同步用广播，控制指令用单播 + ACK。
- 评估"广播风暴"风险：模块数增加时限制转发跳数与频率。
- 时间同步精度决定能否做时隙化调度。

## 3.4 把网络编码引入多机器人系统（2026，IROS）

**链接**：https://arxiv.org/abs/2603.17472

**做了什么**：研究传输层可靠性机制如何影响"自主性-通信"闭环：传统非编码重传会引入与多机器人实时性不匹配的长时延，导致收到的数据已失效；作者主张自适应、因果的网络编码，主动注入编码冗余以匹配时延与吞吐。两个案例：时延/丢包下的协同定位、安全关键的超车决策；作者报告编码方案把超车中止截止时间满足率从 60% 提升到 80%，协同定位精度接近理想基线。

**重点分析**：这篇的结论对 ESP-NOW 很重要：**"可靠"不等于"及时"**。ESP-NOW 的 ACK 重传在丢包时会拉长时延，而协同控制要的是"最新状态"而不是"每包必达"。可行的策略是：状态广播不重传、用冗余编码/多次广播提高"至少收到一次"的概率；关键指令才用重传 + ACK。

**可参考点**：
- 区分"状态类消息"（允许丢、要新）与"指令类消息"（要可靠、可等）。
- 用重复广播/异或冗余替代逐包 ACK 重传，降低时延尾部。
- 把"数据年龄（age of information）"作为通信指标，而不是只看丢包率。

## 工程注记：ESP-NOW 的协议事实与设计建议

以下不是论文结论，是 ESP-NOW 的公开协议特性与本仓库的工程推断，落地前请以 Espressif 官方文档与你自己的实测为准。

- **链路层**：2.4 GHz，基于 Wi-Fi 的免连接传输，支持单播/广播，单包有效载荷上限约 250 字节，单播可带 ACK 与有限重传，广播无 ACK、无重传。
- **没有原生测距与时间同步**：ESP-NOW 不提供 ToF/ RSSI 测距（RSSI 波动大，不适合作为主测距），也不提供节点间时钟同步。UWB 提供测距，时间同步需要额外的协议层（见 04 章）。
- **节点表与规模**：ESP-NOW 需要维护 peer 表，单播对象数量受内存限制；模块数增加时要评估表容量与广播风暴。
- **与 Wi-Fi 共存**：ESP32 的 Wi-Fi 与 ESP-NOW 共享射频，开启 STA/AP 或扫描会引入时延抖动；协同飞行期间应避免 WiFi 扫描与大流量 TCP。
- **建议的消息分层**（推断）：
  1. 控制/模式指令：单播 + ACK + 序号，允许重传，过期丢弃。
  2. 状态广播：广播 + 时间戳 + 序号，不重传，接收端按时间戳丢弃旧值。
  3. 大块数据（日志、参数）：低优先级、分批、可中断。
- **建议的时隙化**：按模块 ID 分配广播时隙（类 TDMA），避免同时发送冲突；时隙长度由最大包长与最坏传播时延决定，需实测。
- **建议的指标**：端到端时延分布（P50/P99）、抖动、丢包率、数据年龄，而不是平均时延。

## 本章综合

| 设计问题 | 结论/做法 | 依据 |
| --- | --- | --- |
| 控制频率怎么定 | 由时延与丢包分布反推，不要把通信当理想 | 3.1 |
| 时延抖动 | 消息分级 + 过期丢弃 + 实时性优先调度 | 3.2 |
| 状态同步 | 广播/冗余优于逐点单播 | 3.3、3.4 |
| 可靠性 | 状态类"要新不要全"，指令类"要全可等" | 3.4 |
| 时间同步 | ESP-NOW 不提供，需单独设计或借 UWB | 04 章 |

**边界**：以上论文的无线链路（802.11、6TiSCH、并发传输）与 ESP-NOW 不完全相同，结论只能作为设计方向，不能直接当性能保证。ESP-NOW 的实际吞吐、时延、丢包必须在你自己的模块数与飞行姿态下实测。
