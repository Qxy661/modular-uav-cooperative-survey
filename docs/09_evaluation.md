# 09 评测方法与实验协议

> RQ8：这个领域用什么指标、什么实验协议证明"协同有效"？为什么通信模型必须在仿真里建模？

## 9.1 问题定义

协同系统的论文结论高度依赖实验设置：模块数、负载、通信条件、故障注入、基线选择。缺乏统一协议导致数字不可横向比较，也让"创新点"难以被验证。本章从 39 篇核心语料中提取可复用的评测实践，并给出面向投稿的实验矩阵。

## 9.2 现有评测实践

| 实践 | 代表工作 | 做法 |
| --- | --- | --- |
| 规模递进 | [10][11][12][14][15] | 2→3→6→8 模块，记录性能随规模变化 |
| 故障注入 | [11][15] | 单模块失效、断连、质心/负载变化 |
| 通信降级 | [21][31][39] | 丢包、时延、带宽/量化限制 |
| 真实通信模型仿真 | [39] | 内嵌 6TiSCH 网络仿真，10–2500 智能体 |
| 系统级对比 | [38] | 按连接方式、控制架构、感知配置横向比较原型 |
| 布局/控制联合评估 | [17] | 用 H2 风格鲁棒性指标比较布局 |
| 嵌入式可行性 | [26][30] | 在 MCU/机载平台报告计算与更新率 |

## 9.3 指标清单

| 维度 | 指标 | 说明 |
| --- | --- | --- |
| 跟踪 | 位置/姿态 RMSE、最大误差 | 分悬停、轨迹、扰动 |
| 协同 | 模块间相对位置误差、载荷份额偏差、内力 | 证明"真的在协同"而非各自飞 |
| 通信 | P50/P99 时延、抖动、丢包率、数据年龄 | 必须与飞行日志同步记录 |
| 容错 | 故障后恢复时间、任务完成率、性能下降 | 对齐 [34] 的韧性度量 |
| 能耗 | 每模块电流/推力、续航 | 分配算法的实际收益 |
| 可扩展 | 模块数 2/4/6/8 曲线 | 验证模块化主张 |

## 9.4 仿真保真度

[39] 的结论是本章最重要的方法论提醒：**理想通信假设下的仿真会高估协同性能**。对 ESP-NOW 系统，仿真至少要建模：丢包率、时延分布、广播冲突、节点数影响，并用实测数据标定参数。

## 9.5 面向投稿的实验矩阵（推断）

| 实验 | 目的 | 变量 | 基线 |
| --- | --- | --- | --- |
| E1 双模块刚性连接 | 验证力估计与分配 | 载荷、连接位置 | 伪逆分配、集中 QP |
| E2 多模块搬运 | 验证协同与规模 | 模块数 2/4/6 | 集中式、分布式一致性 |
| E3 通信降级 | 验证低带宽鲁棒性 | 丢包/时延/广播周期 | 高频通信版本 |
| E4 故障注入 | 验证容错与检测 | 单模块失效、断连、力传感器异常 | 无检测/无重构 |
| E5 消融 | 验证各组件贡献 | 去测力计、去 UWB、去事件触发 | 完整系统 |

报告规范：每个实验给模块数、负载、通信条件、故障脚本、随机种子数、失败运行处理方式；代码/数据尽量开源（参考 [5][6][7] 的开源实践）。

## 9.6 证据强度与局限

- [38][39] 是 B/C 级；其余实践分散在各工作中，未形成统一标准。
- 现有工作的实验规模普遍 ≤ 8 模块，没有大规模（>20）的实机协同搬运证据。
- 没有工作报告"通信降级 × 故障注入"的联合实验；这是 10 章 G7。

**本章结论**：评测的关键不是指标多，而是"通信条件 + 故障条件 + 基线"三件事同时报告；否则数字不可比，创新点也无法被独立验证。
